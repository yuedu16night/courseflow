## 1. 项目概况

CourseFlow 是一个高校选课与排课编排系统，服务**单个活动学期**：学生在容量受限的教学班上选课、退课，教务按 `pre_enrollment → allocation → add_drop → closed` 推进阶段，系统对每个请求给出确定的录取 / 候补 / 拒绝结果并附机器可读原因码。

演示库含 **122 门中文课程、64 个教学班、2 份培养方案、8 个账号**，共 **32 个 REST 端点、11 张表、103 个自动化测试**（LLM 通道默认离线，测试不触碰互联网）。

## 2. 系统的复杂性

### 2.1 结构复杂性

> 分层架构、模块边界、状态/逻辑分离、清晰的 API 接口。

- **分层**：REST 接口层（`app/api.py`，32 个端点，只做映射与 RBAC 守卫）→ 控制平面（`app/services.py` 的 7 个服务）→ 纯领域层 → 仓储层（`app/repositories.py`，系统中唯一写 SQL 的模块）。
- **模块边界**：控制平面只管编排与事务，业务规则全部落在纯领域层。`state_machine` / `policies` / `graph` / `degree` / `timetable` / `curriculum` 都是**无 I/O 纯函数**，可脱离 HTTP 与数据库直接单测。
- **状态/逻辑分离**：状态定义与合法迁移集中在 `state_machine.py` 的声明式转移表，服务层不再写散落的条件判断。
- **清晰的 API 接口**：端点按角色与能力分组（选课 / 课表 / 学业规划、以及阶段、分配、培养方案、审计、事件等管理面），`require(capability)` 统一守卫。
- **服务 API 之上的第二个消费者**：LLM 智能体层（`app/agent`）与浏览器界面并列，只调用同一套服务 API、绝不直接写 SQL；接入它时**未修改任何既有策略、状态机或服务**。

### 2.2 行为与编排复杂性

> 状态机、事件驱动通信、异步控制、版本管理、阶段交接、上下文共享。

- **状态机**：选课有 8 个显式状态（SUBMITTED / VALIDATED / ENROLLED / WAITLISTED / REJECTED / CANCELLED / EXPIRED / DROPPED），由一张声明的转移表驱动，非法迁移无法表达；每次合法迁移都在通知事件总线**之前**写入只追加的 `enrollment_audit`。
- **事件驱动通信**：退课只发布 `section.seat_released`，`WaitlistEngine` 订阅它、按 FIFO 晋升队首候选，晋升前**重跑完整约束链**（等待期间世界可能已变）——选课请求路径里没有任何候补轮询。
- **异步/响应式控制**：席位释放作为事实发布到进程内事件总线，响应式处理与请求路径解耦，主流程不同步等待候补结果。
- **阶段交接**：`pre_enrollment`（只收志愿、不计容量）→ `allocation`（`seed=42` 批量抽签，同种子 ⇒ 同结果；此时直接选课被 `PHASE_LOCKED` 拒绝）→ `add_drop`（先到先得 + 退课 + 候补晋升）→ `closed`（冻结）。每次推进写一份**交接快照**（各教学班 enrolled / validated_pending / waitlisted 计数），阶段之间零状态丢失。
- **上下文共享**：快照即跨阶段共享上下文；智能体层则以登录用户身份行动，会话最多保留 8 轮历史、6 步工具循环，每回合以 `agent.turn` 追加进事件日志。
- **版本管理**：课程目录与培养方案都是**版本化不可变注册表**——变更插入新版本、停用旧版，在途学期保持原语义。
- **对话式编排**：`AgentOrchestrator` 把 14 个既有用例封装为 LLM 可调用的工具，运行「调用 → 观察 → 再调用」循环；模型只负责选择调哪个工具，**写操作不直接执行**，只产出待确认提案，确认后走常规 REST 端点（`propose → confirm → execute`）。
- **降级即确定性**：未配置密钥或端点不可达时，自动降级为离线规则模式（对 7 类意图做加权同义词评分），无网络也能完整运行、行为可复现。

### 2.3 语义与领域复杂性

> 形式化本体、模式、图拓扑、约束系统、数据注册表。

- **形式化本体**：课程分五类（主修 / 专业选修 / 交叉 / 通识 / 个性化），实体覆盖课程、教学班、学期、学生、教师、培养方案，关系包含先修、授课与培养方案规则。
- **图拓扑**：先修关系构成**有向无环图（DAG）**，任何目录变更都做环检测并拒绝成环（`PREREQ_CYCLE`），也可按拓扑学习顺序查询；毕业规划在同一张图上做拓扑排序。
- **约束系统**：一次选课请求依次经过 **`check_duplicate → check_prerequisites → check_timetable → check_credit_limit`** 四项纯函数校验，各自产出机器可读原因码（`PREREQ_MISSING` / `TIMETABLE_CONFLICT` / `CREDIT_LIMIT` / `DUPLICATE_ENROLLMENT` / `ALREADY_PASSED`）。冲突校验覆盖**预选志愿与已录取记录**，并指认是哪一门课撞的。
- **数据注册表**：**两份**版本化不可变注册表——课程目录，以及培养方案（表头 + 规则行，规则分 `all_of` / `choose_n` / `min_credits` 三类）。`enrollment_audit` 与 `event_log` 是只追加的证据表。
- **在此之上的组合规划**：**毕业规划**把先修 DAG 拓扑排序后逐学期学分装箱，输出跨学期路线图，不可行时给 `SEMESTER_LIMIT` / `PREREQ_UNSCHEDULED` 诊断；**课表规划**用有界回溯（节点上限 50,000）为给定课程组合挑无冲突教学班，失败时指出哪两门课「全部教学班两两冲突」。
- **智能体组合搜索**（`PlannerAgent`）：把「单次请求校验」升级为「多课程组合搜索」，在学分上限与课表不重叠约束下带回溯枚举（节点上限 50,000），对每门纳入或排除的课给出原因码——它复用的正是上面的先修 DAG 与约束链。
- **开课编排**（`curriculum.build_offering`）把 122 门课投放到每周 5 天 × 5 个两节连排块上，**刻意调高课程密度**，使同一时间格必然多课撞车——冲突只在「同一学生的选课组合」层面由上面的约束链与规划器消解。

## 3. 交付物与范围

交付：可运行仓库（Python 3.11 / FastAPI / SQLite / pytest，**103 个测试**）；8–12 页架构与复杂度报告（组件架构、Schema、状态机与序列图、扩展性与权衡分析、脚本化端到端轨迹）；现场演示（多名学生走完三个阶段，展示拒绝原因、抽签分配、候补晋升，以及毕业路线图与无冲突课表规划）。

本次只做**单学期、进程内事件**。多学期注册表、分布式事件代理、与真实教务系统的对接，以及按年级 / 专业的优先级分配不在范围内，留待未来工作。
